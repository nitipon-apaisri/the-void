# PLAN.md

Goal: a self-built virtual workspace for ~100 concurrent users, as a desktop app (macOS, Windows; Linux optional).

## Architecture

| Layer          | Choice                   | Notes                                               |
| -------------- | ------------------------ | --------------------------------------------------- |
| Client         | TypeScript, Vite, Phaser | Tiled (`.tmj`) maps                                 |
| Realtime state | Colyseus 0.18            | One room per space (max 100 players each)           |
| Voice / video  | LiveKit                  | Self-hosted SFU (`docker compose up`)               |
| Auth           | Email and password       | Own server: scrypt hashes, signed 7-day tokens      |
| DB             | Postgres                 | Users, spaces, permissions                          |
| Desktop        | Electron                 | Chosen over Tauri for consistent WebRTC and WebGL   |
| Deploy         | Docker Compose on a VPS  | Colyseus, LiveKit (if self-hosted), Postgres, proxy |

## Design rules for 100 users

- Proximity video: subscribe only to players within ~3 tiles; unsubscribe on leave. Never full mesh.
- Position sync at ~10–15 Hz; client interpolates.
- Interest management: send each client only nearby players once the room grows.
- Cap video tiles per user in crowded areas.

## Roadmap

0. **Foundations** (done): layout from `AGENTS.md`, `@void/shared` contract, Oxlint, Prettier, Vitest, `typecheck`, Husky, `.env.example`.
1. **World** (done): Tiled map (`office.tmj`) with wall and desk collision, camera follow, join form, name labels. Placeholder art was replaced in 4b. The server enforces the same collision layer since 4d.
2. **Proximity A/V** (built, self-hosted LiveKit): the room answers a `voice-token` request with a short-lived, room-scoped token; the client subscribes only to players within 3 tiles (with hysteresis, set by `PROXIMITY_TILES`) and has mic and camera toggles. Local dev: `docker compose up -d`, copy `.env.example` to `.env`. Not yet verified with two live browsers, and production needs a real key, `use_external_ip` and TLS (`wss://`).
3. **Accounts** (built and verified in a browser): `/auth/register`, `/auth/login`, `/auth/me` on the game server; scrypt password hashes in Postgres (`t_users`); the room authenticates every join from a signed token and restores name, avatar and last position. Local dev: `docker compose up -d`, `npm run migrate -w server`. Still to do: password reset and email verification (needs a mail provider), profile editing, token revocation. Production: set a strong `AUTH_SECRET`, `CORS_ORIGINS` for the packaged client, `TRUST_PROXY_HOPS`, and TLS.
4. **Space features** (in this order; screen share is done, the rest is planned):
   - **4a. Settings** (built and verified by hand): one settings window with two tabs. _System_: proximity range, mic, camera and speaker choice, volume, key bindings, quality; kept per device in `localStorage`, and in the desktop app through the preload bridge if it needs OS access. _Account_: display name, change password, change email, sign out everywhere (needs token revocation), delete account. Built: proximity range, mic, camera and speaker, volume and movement keys (arrows, WASD or both) in System; name and colour, email and password change (both ask for the current password), sign out other devices, and delete account in Account. Tokens carry a version (`t_users.token_version`) so a password change or "sign out other devices" ends every other login. Still open: other devices stay connected to the room until they next reconnect, a graphics-quality setting waits for 4b, and password reset needs a mail provider.
   - **4b. Better graphic** (built and verified by hand): LimeZu Modern Interiors (paid, licensed, not committed; see AGENTS.md, Art). `npm run assets:import` copies the sheets we use; the map is redrawn with real floors, walls, workstations, a lounge and a meeting room; the 10 premade characters walk and idle in four directions (avatar 0 to 9). Collision comes from a hidden `collision` layer, so what you see and what blocks you can differ. Also built, not yet tried by hand: an `above` map layer so the tops of tall furniture draw over players who walk behind it, a gentler camera follow with a small dead zone, and graphics settings (zoom, frame rate cap, show names). Still open: a lighting pass. 4c builds on this sprite format.
   - **4c. Character customize** (built, not yet tried by hand): a character is five layered parts from the LimeZu generator (skin, eyes, outfit, hair, optional extra), each a style and a colour. Stored as `t_users.look` (`"body.eyes.outfit.hair.accessory"`), validated on the server against `LOOK_COUNTS` in `@void/shared`, and sent to everyone through room state. The client draws the layers into one texture per look the first time it is seen and caches the layer images; a preview with style and colour steppers and Shuffle sits in the sign-up form and in Settings, Account. The old premade `avatar` column is kept, unused. Still open: textures are never freed, and the layer lists follow pack v41.4 (the import warns if the counts differ).
   - **4d. Spaces** (replaces the single hardcoded room and the earlier private-rooms idea, which is dropped for now): every feature below belongs to a space, so this comes first. Order of work:
     - **P0 Spaces, members, roles, user list** (built, not yet tried by hand): `t_spaces` and `t_space_members` (roles owner, admin, member; the last position is kept per space). One Colyseus room per space (`filterBy(["spaceId"])`) and one LiveKit room per space. The server checks membership on join, loads the map's `collision` layer and refuses moves into walls or faster than walking speed (it sends `snap` to put the client back). The client shows a space picker after sign-in (the last space opens by itself; otherwise it asks Join a space or Create a space, and only Create shows the size and style options), a Switch space button, and a People panel with online and offline members, search, and click to walk to someone. Accounts that existed before get one space, "The Void". New spaces use the office template. Roles are used by Roles and members, below.
     - **P1 Invite by link** (built, not yet tried by hand): owners and admins make a link (ask-first or open, 1 day to never); only a hash of the token is stored, and the link is shown once. Opening `/?invite=<token>` signs in, asks "Join X?", then adds the person or files a request. Requests show in the People panel with Let in and Decline, and admins get a toast when someone is waiting (polled every 30 seconds). Each link also comes with a short join code (10 letters and digits, like `K7M2P-9QXA4`, shown once) with the same approval and expiry; people type it under Join a space, in any case, and it goes through the same confirm step as a link. Only an HMAC of the code (keyed with `AUTH_SECRET`) is stored, and wrong codes are limited to 15 per 15 minutes per address. Links and codes can be revoked together; at most 20 are active per space. Still open: the `thevoid://join/...` deep link (desktop polish).
     - **P1 Bigger map, mini map, floating buttons** (built, not yet tried by hand): the office is now 90 x 67 tiles (about 5 times the area) as a 3 x 3 grid of rooms: three open offices, meeting rooms, a lounge, a plaza, a cafeteria and an event lounge, joined by doorways. `npm run assets:import -- --map` regenerates it. A mini map (bottom left) shows walls, people and the camera view, and a click on it walks you there. Floating buttons (bottom right): zoom in and out (0.5x to 3x), show me, and show or hide the mini map. Still open: interest management (each client only gets nearby players) before 100 people use a map this size, and the saved positions of people from the old map fall back to the spawn when they land in a wall.
     - **Trackpad zoom and drag to pan** (built, not yet tried by hand): pinch (or Cmd/Ctrl + wheel) zooms smoothly between 0.5x and 3x, toward the pointer when you have panned away; two-finger scroll over the map zooms the same way; hold and drag the map to pan; a plain click still walks. The view returns to you on movement, a click-to-walk or Show me. A pinch is not saved; the Settings zoom stays a steady level.
     - **P2 Claim a table** (built and tried by hand): the 60 desks are objects on a `tables` layer of `office.tmj` (the import script writes them with the map; ids are the object ids). Stand inside a desk's box (the desk and the seat in front of it) and a bar at the bottom offers Claim desk or Release desk; the owner's name shows on the desk. One desk per person and one person per desk, per space: the room checks the distance, then the database settles races (`t_table_claims`, unique indexes). Claims survive restarts. Removing a member releases their desk. Still open: moving to another desk needs a release first, and meeting tables are not claimable.
     - **P2 Waving** (built and tried by hand; going to a person from the People panel now runs at double speed): a "Wave at X" button appears above the voice bar when someone is within four tiles; the room checks the range (spamming is fine; only more than 20 a second is dropped), then tells only the waver and the target. Both see a hand float over the waver; the target also gets a toast. Nothing is stored. Still open: a desktop notification when the window is in the background (needs the notifications work), and waving at someone from the People panel.
     - **P3 Decoration (furniture)** (built and tried by hand): every member gets a Decorate button (above the map buttons) that opens groups of pieces (Tables, Chairs, Office, Kitchen, Storage, Bedroom, Bathroom, Plants, Rugs, Wall, Doors, Any tiles); a group lists its pieces. The 10 ready-made ones (plant, chair, desk, desk chair, rug, coffee table, bookshelf, sideboard, whiteboard, meeting table; `FURNITURE` in `shared/src/furniture.ts`) sit first in their groups. Pick one and a ghost follows the pointer on the tile grid (red when it does not fit); click to place; "Remove pieces" outlines a placed piece and click removes it; "Empty the whole space" (after a confirm) clears every placed piece and moves the space to the Empty room template, so the map's own furniture goes too (the room closes and clients reload); The other 115 pieces come from `ART_CATALOG` in `shared/src/art-catalog.ts` (read off the sheets by eye, so a few may be a tile off), and the "Any tiles" group to drag over the generic, conference, floors or walls sheet (up to 10 x 10, walkable or solid; the id is `x:<sheet>:<sx>:<sy>:<w>:<h>:<solid>` and the room checks it against the sheet size); Esc finishes. Only owners and admins can empty the space. Pieces are saved per space (`t_furniture`), at most 300, and sent to everyone through room state. The room refuses a spot outside the map, on a wall or another blocking piece, in a desk's claim box, or under someone's feet, and a placed piece blocks movement on both server and client (the mini map redraws). Tall pieces draw their top rows over players. Anyone may remove what they placed; owners and admins may remove anything (a piece from before placers were recorded is for owners and admins). Still open: no way back to the old template, and no rotate or move.
     - **Sitting** (built and tried by hand): the 60 desk chairs and 60 meeting chairs are objects on a `seats` layer of `office.tmj` (point plus facing), and a placed chair or desk chair is a seat too. Stopping within about 1.6 tiles of a free chair sits you down by itself (no button); the room snaps you onto it, others see you sitting, and any movement key or click puts you back on your feet (at the spot you sat down from, or the nearest open one). One person per seat, and a removed chair stands its sitter up. The desk chairs are now drawn by the client and lifted 28 px so they tuck under the desk (`SEAT_LIFT` in `scripts/import-art.mjs`). The character sheets have sitting poses for right, left and down only, so a chair that faces up (the desk chairs) shows the standing back view a little lower. Still open: the lift and seat offsets are guesses to tune by eye, and chairs have a fixed facing (no rotation).
     - **Space templates** (built, server checked; not yet tried by hand): a new space picks Classic office, Empty room (bare walls and floor, nothing to remove, for decorating from scratch), Open plan (one light floor, 44 desks, meeting rooms, lounges) or Studio (a 50 x 39 room in the middle of the map, 12 desks). `t_spaces.template` already existed; the server reads every template map at start and a room uses its space's map, so walls, desks and seats follow the template. The picker in the space list shows a thumbnail of each. Still open: templates cannot be changed after creation, and the art is still the one LimeZu set (see the asset browser for more pieces).
     - **Space sizes** (built, typechecked; not yet tried by hand): a new space also picks small (60 x 45), medium (90 x 67, what every earlier space is) or large (130 x 96) in the picker, whose thumbnails follow the size. `t_spaces.size` (new migration, default `medium`) is stored with the space; the server loads a map per template and size (`mapName` in `@void/shared`) and checks each file against `SPACE_SIZE_DIMENSIONS`. Room plans in `scripts/import-art.mjs` scale with the size (office is 2 x 2, 3 x 3 or 4 x 4 rooms; open plan and studio add desk rows and lounges); the medium maps are byte-identical to the ones committed before. The spawn is no longer a constant: both sides use `findSpawn`, the free spot nearest the map centre. Still open: size cannot be changed after creation, the client loads every map at start (about 2.4 MB of JSON, so load only the chosen one if it grows), and the small and large layouts want a look by eye.
     - **Roles and members** (built, server checked; not yet tried by hand): owner, admin and member now differ. Only the owner changes roles (Make admin, Make member) or hands the space over (Make owner: they become the owner, the old owner an admin, in one statement); the owner removes anyone, an admin removes plain members; anyone but the owner can leave (Leave space in the People panel). The rules are `canRemoveMember` and `canChangeRole` in `@void/shared`, checked on the server in `member.service.ts` (`PATCH` and `DELETE /spaces/:id/members/:userId`) and used by the panel's row menu (the "..." on a row). A removal frees the person's desk, tells the room over a Colyseus presence channel (`memberChannel`), and the room sends `removed` to that client (it shows a toast, then the space picker) and `members-changed` to everyone else (they reload the list; someone whose own role changed reloads the page). Closing an account hands each space it owns to its longest-standing admin, else member, and closes a space nobody else is in. **Ban** (built, server checked; not yet tried by hand): "Ban" in a row's menu (same rules as Remove, never yourself) takes the person out, frees their desk, declines a pending request and records them in `t_space_bans` in one statement (`ban.repository.ts`); the room kicks them like a removal. A banned person's link or code answers as if it were dead (`invite.service.ts`), and `addMember` and approving a request refuse them in SQL too. Owners and admins see a Banned list in the People panel (`GET /spaces/:id/bans`, `PUT` and `DELETE /spaces/:id/bans/:userId`) and can Unban; the person then needs a new link or code. Still open: nothing logs who removed whom, a role change reaches an open page by reloading it, and a ban is per space, not per account.
     - **Nice to have**: text chat (was 4e), status and do-not-disturb, follow a person, desktop notifications for waves and invites, kick and ban, a broadcast or stage zone for all-hands talks.
   - Screen share, browser part (built and verified with two browsers): a Share screen toggle; viewers receive only the nearest sharer (`MAX_SCREEN_SHARES`); tokens may publish only mic, camera and screen. Desktop part (built and verified on macOS): the renderer shows its own picker (`ui/screen-picker.ts`), the main process lists sources over IPC and answers `getDisplayMedia` with the one that was picked. macOS needs Screen Recording permission, and packaging (step 7) needs the usage strings in `Info.plist`. Windows is untested.
5. **Admin**: roles, map editing workflow, room permissions.
6. **Desktop polish**: preload script, tray, notifications, global push-to-talk, deep links (`thevoid://join/...`), screen-source picker.
7. **Packaging**: electron-builder for macOS `.dmg` and Windows `.exe` (AppImage optional); macOS signing and notarization (Apple Developer account); Windows code signing; auto-update.
8. **Load test** (built and run): `npm run load -- --bots 100 --seconds 30 --size large` starts the real room with an in-memory backend (no Postgres) in a child process and joins bots that walk to random spots at the client's rate (12.5 moves a second). It reports server CPU, event loop delay, memory, bandwidth per client and moves the server corrected, and fails if a bot cannot join, is dropped, or event loop p99 passes 50 ms. Result with 100 bots on a laptop: about 9% of one core, event loop p99 under 25 ms (the timer itself adds about 10), 110 MB, 17 KB/s out per client on both the medium and the large map, so interest management is not needed yet. LiveKit is covered by `test/load/voice.sh` (16 rooms of 6 people against a local LiveKit, `lk load-test` underneath): voice only about 2 Mbps out in total, every camera on at medium resolution about 120 Mbps (1.1 to 1.4 Mbps per person) at about one core with at most 0.1% packet loss and no subscriber errors, with the generators on the same laptop. Not covered: the HTTP API and the database, screen shares, a real network, and real browsers (100 Phaser clients are a client frame-rate question). Test the real client with a few windows before a launch.
